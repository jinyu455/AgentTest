# 需求分析文档

## 1. 系统概述

EmoAgent 是一个面向文本情绪分析的智能 Agent 系统，适用于聊天记录、评论文本、客服会话、内容审核文本等场景。系统通过多 Agent 协作完成文本路由分类、表层情绪识别、反讽识别、混合情绪识别与最终结果融合，并将分析结果以结构化 JSON 形式返回给前端或第三方系统。

系统由三个主要子系统组成：Web 前端、Spring Boot 后端服务、Python FastAPI Agent 服务。前端负责用户登录、聊天交互、情绪洞察和历史数据展示；后端负责认证授权、会话与消息持久化、统一 API、Agent 服务编排；Agent 服务负责调用大模型并完成情绪分析任务。

本系统仅处理文本输入，不处理语音、图片、视频等多模态数据。系统重点关注情绪分析准确性、接口稳定性、权限控制、调用日志和数据可追溯性。

## 2. 需求概述

### 2.1 目标

本系统的开发目标是构建一个可云端部署、可通过后端自动调用的文本情绪分析 Agent 平台，解决传统情绪分析系统对反讽、混合情绪和模糊表达识别不足的问题。

系统应达到以下目标：

- 支持文本输入的基础情绪识别，初始覆盖开心、悲伤、愤怒、焦虑、厌烦、中性等情绪类型。
- 支持反讽文本识别，并对表层情绪和真实情绪进行区分。
- 支持混合情绪、模糊情绪识别，输出主情绪、次情绪、比例、强度和置信度。
- 支持统一结构化结果输出，便于前端展示、后端保存和第三方系统集成。
- 支持用户认证、会话保存、历史记录查看和情绪趋势展示。
- 支持调用日志、异常处理、统计分析和后续扩展。

### 2.2 运行环境

系统采用前后端分离和独立 Agent 服务部署方式。前端可通过静态 Web 服务运行；后端运行于 Java 17 与 Spring Boot 环境；Agent 服务运行于 Python 环境，通过 FastAPI 提供 HTTP 接口；数据库采用 SQLite 作为轻量持久化方案。

开发与测试阶段可在单机运行三个服务；正式部署时建议将前端、后端、Agent 服务和数据库存储进行隔离部署，并通过环境变量配置大模型 API 地址、模型名称和密钥。

### 2.3 用户的特点

| 用户类型 | 用户特点 | 主要使用目标 |
|---|---|---|
| 普通用户 | 关注聊天体验和情绪反馈，技术背景要求低 | 输入文本、查看情绪分析结果和历史记录 |
| 运营人员 | 关注文本情绪分布、用户状态和趋势 | 查看情绪洞察、筛选历史记录、辅助运营判断 |
| 客服质检人员 | 关注客服对话中的负面情绪、反讽和风险表达 | 审核对话质量、定位异常情绪文本 |
| 内容审核人员 | 关注文本态度和潜在风险 | 辅助判断文本情绪倾向 |
| 管理员 | 具备系统配置和数据管理职责 | 管理用户、权限、日志和全量数据 |
| 第三方系统调用方 | 通过 API 自动提交文本并接收结果 | 批量或实时调用情绪分析服务 |

### 2.4 关键点

本系统需求中的关键点包括：

- 多 Agent 分工：Router Agent、Emotion Agent、Sarcasm Agent、Mix Agent、Judge Agent 分别承担不同分析职责。
- 结构化输出：所有 Agent 输出应符合预定义 schema，最终结果便于后端解析和持久化。
- 反讽与混合情绪识别：系统需要处理“表层积极但真实负面”“同时存在多种情绪”等复杂表达。
- 前后端与 Agent 接口契约：后端需稳定编排 Agent 服务，前端需统一消费后端返回结果。
- 数据安全：用户身份认证、权限隔离、敏感数据保护和调用日志审计。
- 可扩展性：后续可扩展更多情绪标签、批量分析、告警通知和管理后台能力。

## 4. 需求规定

### 4.1 软件系统总体功能结构

系统总体功能结构如下：

```text
EmoAgent
├─ Web 前端
│  ├─ 登录 / 注册
│  ├─ 聊天工作台
│  ├─ 实时情绪洞察
│  └─ 历史记录与趋势展示
├─ Spring Boot 后端
│  ├─ 用户认证与 JWT 鉴权
│  ├─ 会话与消息管理
│  ├─ 情绪分析统一接口
│  ├─ Agent 服务编排
│  ├─ 数据持久化
│  └─ 异常处理与日志
└─ Python Agent 服务
   ├─ Router Agent 文本路由分类
   ├─ Emotion Agent 表层情绪识别
   ├─ Sarcasm Agent 反讽识别
   ├─ Mix Agent 混合情绪识别
   └─ Judge Agent 结果融合与判定
```

核心业务流程如下：

```text
用户/第三方系统提交文本
        ↓
后端校验请求与身份
        ↓
后端调用 Agent 服务
        ↓
Router 判断文本类型
        ↓
Emotion 识别基础情绪
        ↓
按需调用 Sarcasm / Mix
        ↓
Judge 融合最终结果
        ↓
后端保存会话、消息与分析记录
        ↓
前端展示情绪、强度、置信度、解释和历史趋势
```

| 项目 | 内容 |

### 4.3 非功能性需求

#### 4.3.1 性能需求

单条文本分析在正常网络和模型服务可用情况下应尽量控制在 500ms 至 3s 内返回。前端页面交互应在 1s 内响应用户操作。历史记录和统计数据查询应支持分页或限制返回数量，避免一次性加载过多数据。

#### 4.3.2 并发性需求

系统初始目标支持中小规模使用场景，后端应支持至少 50 个并发用户访问；Agent 分析接口应具备扩展到 100 TPS 峰值调用的设计空间。对于高并发场景，应通过限流、缓存、队列或横向扩展 Agent 服务降低压力。

#### 4.3.3 安全性需求

系统应提供注册、登录、JWT 鉴权和接口访问控制。用户只能访问本人或权限范围内的数据。系统应保护 API Key、JWT 密钥等敏感配置，不应将密钥写入前端代码或公开仓库。调用日志应避免明文暴露敏感文本，必要时增加脱敏处理。

#### 4.3.4 可用性需求

系统界面应简洁直观，普通用户无需专业训练即可完成登录、文本输入、结果查看和历史查询。情绪结果应包含情绪类型、强度、置信度和简要原因，便于用户理解。当前端、后端或 Agent 服务异常时，应给出可理解的错误提示。

#### 4.3.5 可靠性需求

系统应具备异常处理能力，避免单个 Agent 调用失败导致整个服务不可用。对于模型超时、返回格式异常、数据库写入失败等情况，应记录日志并提供降级处理。数据保存应保证会话、消息和分析记录之间的一致性。

#### 4.3.6 可维护性需求

系统应保持清晰的模块边界：前端负责展示与交互，后端负责业务接口与持久化，Agent 服务负责模型分析。后端 DTO、实体、仓储、服务、控制器应分层组织；Agent 模块应按 router、emotion、sarcasm、mix、judge 分包管理。核心接口和 schema 应保持文档化，测试用例覆盖主要 Agent、后端服务和关键业务流程。
